# 명세를 기준으로 진행하는 TDD

사용자가 요청한 단계까지만 수행한다. 답변과 테스트 이름, 문서는 한국어로 작성한다.

## 작업 전 확인

- 적용되는 AGENTS.md와 기준 SPEC.md, 기존 테스트를 읽는다. 명세에 없는 동작이 필요하거나 요구사항이 애매하면 먼저 질문한다.
- 변경할 파일 목록과 이유를 편집 전에 알린다. 보호 파일 및 문서 승인 규칙은 프로젝트 지침을 따른다. 이 스킬 자체는 수정 권한을 부여하지 않는다.
- fee-kata 연습에서는 fee-kata/SPEC.md를 기준으로 삼고 폴더 밖의 프로젝트 파일을 수정하지 않는다. 다른 프로젝트에는 이 경로와 도구를 강제하지 않는다.

## 테스트 작성과 실패 확인

1. 예시표가 있으면 각 행을 독립된 테스트 하나로 옮긴다. 입력, 기대 결과, 경계값을 그대로 유지하고 테스트 이름에 조건과 결과를 한국어로 적는다.
2. 오류 계약이 Error와 message를 지정하면 오류 발생 여부뿐 아니라 오류 유형과 정확한 message도 검증한다.
3. fee-kata에서는 node:test와 node:assert/strict를 사용하고, `const { transferFee } = require('./fee');`로 함수를 불러온다. 새 라이브러리는 추가하지 않는다.
4. 테스트를 작성하거나 수정한 직후 실행한다. fee-kata의 명령은 `node --test fee-kata/fee.test.js`다.
5. 구현 파일이 없어 모듈 로딩에 실패하면 그 사실을 보고한다. 파일 단위 실패를 개별 테스트 모두의 실패로 표현하지 않는다. 개별 테스트가 실행되지 않았다는 점을 명시한다.
6. 사용자가 테스트만 요청했거나 구현 파일을 만들지 말라고 했다면 여기서 멈춘다.

## 최소 구현과 재실행

1. 구현이 요청된 경우 테스트 실패를 확인한 뒤, 명세를 충족하는 가장 단순한 코드를 작성한다. 예시 입력별 값을 하드코딩하지 말고 요구사항의 규칙을 구현한다.
2. 기존 테스트와 명세를 바꿔 통과시키지 않는다. 실패 원인을 구현에서 해결한다. 명세와 테스트가 충돌하면 임의로 수정하지 말고 질문한다.
3. 명세에 없는 검증, 기능, 라이브러리, 리팩터링을 추가하지 않는다.
4. 구현 직후 같은 테스트 명령을 실행한다. 실패하면 원인을 수정하고 다시 실행한다.
5. 리팩터링은 요청 범위 안에서 필요할 때 수행하고, 변경 직후 테스트를 다시 실행한다.

## 완료 보고

- 생성하거나 변경한 파일 목록과 주요 동작을 적는다.
- 실제 실행한 테스트 명령과 통과·실패 개수를 적는다. 로딩 오류와 개별 테스트 결과를 구별한다.
- 보호 파일을 수정하지 않았다면 `고치면 안 되는 파일: 안 고침`이라고 적는다. 승인받아 수정했다면 파일과 이유를 적는다.
- 실행하지 못한 검사나 확인하지 못한 사항을 통과로 쓰지 않는다.
