# 회사 소개자료 자동 갱신 및 지원 기회 안내 PoC

이 문서는 대화에서 구체화한 최신 기획을 정리한 검토용 문서다. 승인된 요구사항 명세를 대신하지 않으며, 아래 가상 사업의 수치와 시나리오는 제안 상태다. 코드는 작성하지 않는다.

## 1. 주제와 고객

**회사의 재무·제품·성과 변화를 반영해 기업 소개자료를 갱신하고, 지원사업 조건의 변화를 알려 주는 AI 도우미**

첫 고객은 금융이력이 짧고 금융 업무 전담자가 없는 초기 소기업 대표자다. 대표자가 사업에 집중하면서도 회사의 현재 상태를 설명하고, 대출·지원사업·정부 정책사업 신청 기회를 확인하도록 돕는다.

해결하려는 문제는 다음과 같다.

- 회사의 매출·제품·성과가 바뀔 때마다 소개자료를 반복해서 수정해야 한다.
- 소개자료가 오래되면 현재 사업 상태와 새로운 성과를 충분히 설명하기 어렵다.
- 회사 상황이 바뀌었을 때 지원사업의 조건을 다시 확인하는 데 시간이 든다.

은행에 이미 있는 일반적인 제출 서류 체크리스트와 제출 양식 제공은 이번 PoC 범위에서 제외한다. 핵심 가치는 회사 정보의 지속적인 갱신과 그 변화에 따른 지원 기회 재확인이다.

## 2. 학습자료와의 연결

`docs`에 있는 다음 자료의 문제의식을 고객 경험으로 연결한다. 실제 제도의 최신 조건을 검증하거나 그대로 구현하는 기획은 아니다.

| 자료 | 연결할 문제의식 | 서비스에 반영할 방향 |
|---|---|---|
| 초기 스타트업 금융: 은행은 거래이력 없는 기업의 성장성을 어떻게 평가할 것인가 | 초기기업은 재무·거래 이력이 짧아 사업의 성장성과 위험을 설명하기 어렵다. | 기업의 재무·제품·성과를 최신 자료로 정리해 설명을 돕는다. |
| 소상공인 특화 신용평가(SCB) 도입에 따른 은행의 데이터 기반 여신 전략 | 매출·업력 등 사업 데이터가 기존 금융정보를 보완할 수 있다. | 회사 정보와 변화의 근거를 구조화한다. |
| 대안 신용평가: 금융 포용의 기회와 새로운 배제의 위험 | 정보 부족과 불투명한 판단은 새로운 배제로 이어질 수 있다. | 조건 비교의 근거를 보여 주고, 모르는 정보는 정보 부족으로 표시한다. |

회사 소개자료 정리는 신용평가와 별개다. 이 PoC는 신용점수, 대출 승인 가능성, 사업 선정 확률을 산출하지 않는다.

## 3. 핵심 기능과 실행 흐름

### 중심 기능: 회사 소개자료 갱신

대표자가 새 회사 정보를 입력하면 시스템은 기존 정보와 비교해 변경 항목을 찾는다. AI는 해당 항목에 연결되는 소개자료 초안을 갱신하고, 이전 내용·새 내용·변경 근거를 보여 준다. 대표자가 확인한 초안을 사용할 소개자료로 확정하는 방식을 제안한다.

대표자 확인 후 확정하는 방식은 아직 최종 확정되지 않은 제안이다.

### 연결 기능: 지원사업 조건 재비교

업데이트된 회사 정보를 바탕으로 가상 지원사업 2종의 조건을 다시 비교한다. 결과는 충족·미충족·정보 부족과 판단 근거로 표시한다. 서류를 갖췄는지와 신청 조건을 충족하는지는 서로 다른 문제이며, 이번 범위에서는 일반적인 서류 준비 점검을 제외한다.

### 연결 기능: 사업별 보완 정보 안내

선택한 사업의 조건을 확인하는 데 부족한 정보와 다음 행동을 안내한다. 예를 들어 제품 개선 실적의 날짜나 실제 출시 여부가 없다면 해당 사실을 확인하도록 안내한다.

기본 흐름은 다음과 같다.

1. 대표자가 회사 정보를 입력하거나 변경한다.
2. 시스템이 이전 정보와의 차이를 확인한다.
3. AI가 회사 소개자료의 관련 부분을 갱신하고 근거를 표시한다.
4. 가상 지원사업 2종의 조건을 재비교한다.
5. 대표자가 변경 내용을 검토하고 필요한 사실을 보완한다.

조건 비교는 명시된 규칙으로 처리하고, AI는 문장 정리·요약·변경 설명에 활용하는 구성을 제안한다.

## 4. 회사 소개자료 정형 포맷 제안

정해진 항목에 사실을 저장하고, AI가 그 사실을 바탕으로 설명을 작성한다.

| 항목 | 관리할 내용 | 갱신 방식 |
|---|---|---|
| 회사 기본정보 | 업종·소재지·업력·직원 수 | 대표자가 입력한 정보 반영 |
| 재무 현황 | 연매출·기준 기간 | 금액과 기준 기간을 함께 갱신 |
| 제품·기술 | 제품 설명·주요 기능·출시 상태·기술 구성도 | 입력 정보와 확인 가능한 기술 근거로 초안 작성 |
| 주요 성과 | 출시·계약·개발 완료 내역 | 날짜와 근거를 함께 관리 |
| 변경 이력 | 이전 내용·새 내용·변경 근거 | 변경된 항목과 관련 설명 표시 |

갱신 시 적용할 원칙은 다음과 같다.

- 입력하지 않은 사실을 AI가 임의로 채우지 않는다.
- 금액은 원 단위 정수로 다루고, 수치에 기준 기간을 붙인다.
- 매출 증가·감소는 비교 기준과 기간이 맞는 경우에만 설명한다.
- 코드 추가, 개발 완료, 실제 출시, 고객 사용 실적을 구분한다.
- 근거가 부족하면 확인할 항목으로 표시한다.
- 기존 문서 전체를 매번 다시 쓰기보다 변경된 정보와 관련된 부분을 갱신한다.

## 5. 가상 지원사업 2종 제안

모든 사업명과 조건은 PoC용 가상 설정이다. 실제 정책사업의 자격 조건이 아니다.

| 사업 | 조건 |
|---|---|
| A. 초기 사업화 지원 | 업력 36개월 이하이면서 연매출 100,000,000원 이하 |
| B. 제품 고도화 지원 | 업력 60개월 이하이면서 출시 제품을 보유하고, 최근 6개월 내 기능 개선 실적을 보유 |

판정 규칙 제안:

- 조건 중 하나라도 명확히 맞지 않으면 미충족으로 표시한다.
- 미충족 조건은 없지만 판단에 필요한 정보가 없으면 정보 부족으로 표시한다.
- 모든 조건을 확인했고 모두 맞으면 충족으로 표시한다.
- 결과마다 사용한 회사 정보와 비교 조건을 함께 보여 준다.
- 조건 충족은 실제 신청 자격의 공식 확인이나 선정·대출 승인을 의미하지 않는다.

## 6. 회사 상황 4개와 시연 제안

아래 표는 가상 회사 상태 또는 상태 변화를 나타낸다. 적지 않은 정보는 추가로 설정해야 하며, 임의로 채워 판정하지 않는다.

| 상황 | 회사 정보 또는 변화 | 소개자료 갱신 | 조건 비교에서 보여 줄 결과 |
|---|---|---|---|
| ① 초기 상태 | 업력 36개월, 연매출 100,000,000원, 출시 전 | 초기 소개자료 작성 | A 충족, B 미충족 |
| ② 매출 변경 | ①에서 연매출을 100,000,001원으로 변경 | 재무 수치와 관련 설명 갱신 | A가 충족에서 미충족으로 변경, B는 미충족 유지 |
| ③ 제품 성과 추가 | 업력 60개월, 출시 제품 보유, 최근 6개월 내 개선 실적 입력 | 제품·성과 설명 갱신 | A 미충족, B 충족 |
| ④ 근거 부족 | 업력 60개월, 출시 제품 보유, 개선 실적 여부는 알 수 없음 | 확인된 사실만 반영하고 확인할 항목 표시 | A 미충족, B 정보 부족 |

핵심 시연은 같은 회사의 정보가 바뀌면서 소개자료와 지원사업 비교 결과가 함께 바뀌는 모습이다. 36개월·60개월 및 연매출 1억원 경계의 포함 여부를 보여 준다.

## 7. GitDiagram 활용 검토

GitDiagram은 GitHub 저장소의 기술 구성을 다이어그램으로 설명하는 서비스다. 공식 안내에 따르면 저장소의 파일 구조·README·일부 소스 파일을 분석하고, 구성 개요와 Mermaid 다이어그램을 제공한다. AI가 읽을 수 있는 Markdown과 읽기 전용 MCP도 제공한다.

다만 완전한 의존성 분석 결과는 아니며, 저장된 다이어그램은 생성 당시의 상태다. 최신 코드 반영에는 재생성이 필요할 수 있다.

출처: [GitDiagram 공식 활용 안내](https://gitdiagram.com/visualize-codebase), [공식 저장소](https://github.com/ahmedkhaleel2004/gitdiagram). 확인일: 2026-10-26.

### 제안하는 역할

GitDiagram은 소프트웨어 기업의 제품·기술 소개를 갱신하는 확장 기능으로 활용한다. 일반적인 초기 소기업 모두가 저장소를 보유한다고 가정하지 않는다.

1. 이전에 확인한 커밋과 현재 커밋을 비교해 변경 근거를 수집한다.
2. 기술 구성도와 관련 파일을 확인한다.
3. AI가 회사 소개자료 중 제품·기술 설명의 수정 초안을 만든다.
4. 대표자에게 변경 전후와 근거를 보여 준다.
5. 실제 출시 여부 등 코드만으로 확인할 수 없는 사실을 보완한다.

변경 탐지는 커밋 비교가 맡고, GitDiagram은 기술 구조를 설명하는 보조 수단으로 활용한다. 다이어그램 표현의 변화만으로 실제 개발 변화를 판단하지 않는다. 문서 수정과 변경 이력 관리는 별도의 기능이 필요하다.

### 예시

| 구분 | 내용 |
|---|---|
| 확인한 코드 변경 | 다국어 처리 모듈과 관련 테스트 추가 |
| 문서 수정 제안 | 다국어 지원 기능 개발에 관한 설명 추가 |
| 대표자 확인 필요 | 실제 출시 여부, 지원 언어, 고객 사용 여부 |
| 사업 조건 반영 | 출시된 제품의 개선 실적인지 확인한 뒤 조건 비교에 반영 |

코드 변경을 근거로 매출 증가, 시장 성과, 고객 확보를 추정하지 않는다.

### 확인한 연동 상태

공식 문서에서 MCP와 Markdown 제공 방식을 확인했다. 현재 세션의 연결 도구와 플러그인 검색에서는 GitDiagram을 찾지 못했다. 실제 MCP 연결, 다이어그램 생성, 저장소 변경 추적, 문서 자동 갱신 호출은 검증하지 않았다.

## 8. PoC 범위와 미확정 사항

추천 범위는 입력 기반 소개자료 갱신을 중심으로 가상 지원사업 2종과 회사 상황 4개를 연결하는 것이다. GitDiagram 연동은 소프트웨어 기업용 확장으로 둔다.

다음은 현재 범위에서 제외한다.

- 일반 제출 서류 체크리스트와 은행 제출 양식 제공
- 실제 사업 공고 전체 수집과 실시간 정책 동기화
- 외부 은행·세무 데이터 연동
- 신용점수·선정 확률·대출 승인 가능성 산출
- 자동 지원서 제출

요구사항 확정 전에 정해야 할 사항:

- ‘핵심 사업 2개’를 가상 지원사업 2종으로 해석하는 것이 맞는지
- 두 사업의 구체적인 조건과 회사 상황 4개의 최종 값
- 업력 계산 기준일, 연매출 기준 기간, 최근 6개월의 날짜 경계
- 회사 소개자료의 최종 항목과 대표자 확인·확정 방식
- GitDiagram을 이번 PoC의 실제 연동 대상으로 포함할지
- 저장소가 없는 기업의 기술·성과 갱신은 직접 입력만으로 처리할지

이 문서 작성으로 SPEC.md 1장의 요구사항이나 이후 설계·테스트·작업 목록이 승인된 것은 아니다.
